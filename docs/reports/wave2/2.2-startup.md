# Wave 2.2: proxy and mod loading (startup without the loader lock)

Branch: `worktree-agent-a11bdb50608815de7`, based on `modernize` @ f9acdc2 (Wave 2.1).
Status: built, **not tested in-game yet** (🎮 needed, see "Smoke test").

## What changed and why

### 1. Proxy (`LoaderAutoInjector/`, `xinput1_3.dll`)
- Before: on the first `DLL_THREAD_ATTACH` the proxy "injected" MDML into its own process:
  `OpenProcess(PROCESS_ALL_ACCESS)` + `VirtualAllocEx` + `WriteProcessMemory` + `CreateRemoteThread(LoadLibraryA, "MDML.dll")`.
  These are remote-process APIs used on the own process (and are exactly what anti-cheat/AV heuristics look for).
- Now: same trigger (first `DLL_THREAD_ATTACH`, `hooked` flag unchanged), but `Loader::LoadModLoader(hinstDLL)` only
  calls `CreateThread`. The thread routine gets the proxy's own path with `GetModuleFileNameW(proxy)`, replaces the
  file name with `MDML.dll` and calls `LoadLibraryW` on that **full path**. Nothing is loaded inside `DllMain`.
- Before, `LoadLibraryA("MDML.dll")` found MDML through the application directory, which is the same folder
  (`Binaries/Win64`), so the resolved file is the same; the full path just removes the search-order dependency.
- Failures (no path, `LoadLibraryW` error code, `CreateThread` failure) go to `OutputDebugStringW` (visible in
  DebugView); the proxy has no log file. Before, failures were silent.
- No STL in the proxy any more (fixed `wchar_t` buffer of 32768, `wcsrchr`/`wcscat_s`/`swprintf_s`).
- Exports unchanged (12 XInput forwards, same ordinals; pefile). KERNEL32 imports: `OpenProcess`, `VirtualAllocEx`,
  `WriteProcessMemory`, `CreateRemoteThread` are gone; new are `CreateThread`, `GetModuleFileNameW`, `LoadLibraryW`,
  `GetLastError`, `OutputDebugStringW`. `LoadLibraryA` stays (loads the system `xinput1_3.dll`, unchanged).
  MDML.dll no longer imports `CreateRemoteThread`/`VirtualAllocEx` (`OpenProcess`/`WriteProcessMemory` remain, used
  by `Utilities/Memory.h`, out of scope).

### 2. MDML startup (`dllmain.cpp`, `MDML.cpp/.h`, `HooksManager.cpp/.h`)
- `DllMain(DLL_PROCESS_ATTACH)` → `MDML::Start(hModule)`, which only does `CreateThread(InitThread)` (+ `CloseHandle`).
  `MDML::Start` now takes the module handle (exported signature changed from `Start()` to `Start(HMODULE)`;
  nothing outside MDML calls it). The MDML folder comes from that handle instead of `GetModuleHandleA("MDML.dll")`.
- **One init thread** replaces "DllMain + separate InitHooks thread". It runs, in this order:
  1. `SetupProfile` (unchanged: ini, log dir, console, loggers, DX11 check, NoOverwrite walk/parse, PDB/pattern
     resolution, manual defs) — now **outside** the loader lock.
  2. `HooksManager::SetupHooks()` (was the `InitHooks` thread body, now called synchronously):
     MinHook init → overwrite links (`CreateSysLinks` / `DeleteSysLinks(true)`) → pak hooks → `ModLoader::LoadMods()`
     → game hooks (`InitGameState`, `BeginPlay`, `UWorld::Tick`) → UI logic thread → (`HookDX` if `DelayGUISpawn=0`).
- The init thread catches `std::exception`/`...` and logs `Loader initialization failed: …` (Critical) instead of
  terminating the game. Before, an exception in `SetupProfile` happened inside `DllMain`, where the CRT turns it into
  a failed `LoadLibrary` (game runs without MDML); an exception on the old `InitHooks` thread terminated the game.
- New log lines for the timing question (Q8): `Profile setup took N ms`, `Pak overwrites loaded (N ms after process
  start, M UObjects exist)`, `Loader setup finished (N ms after process start)`. `M` is read from
  `GUObjectArray.ObjObjects.NumElements` (offset 0x10 + 0x14, PDB-verified in code-inventory Appendix A), one 4-byte
  read, log only.
- `MDML::ShutDown`: the "Shutting down" log is skipped if the logger does not exist yet (process exits before the init
  thread reached `Log::Init`; before 2.2 the logger always existed because setup ran inside `DllMain`). The rest of
  `ShutDown` is unchanged; `HooksManager::ShutDown` is safe without MinHook init (`MH_ERROR_NOT_INITIALIZED`) and only
  deletes links when `ModOverwritesEnabled` (set after `Log::Init`).
  **Not touched:** `_fcloseall()` + logger double delete (code-inventory 2.3, B-list) — still UB at exit.

### 3. Mod loading (`Mod/ModLoader.cpp/.h`)
- `ModLoader::InjectDLL` (per-mod `CreateRemoteThread(LoadLibraryA)`) removed. Mod DLLs are loaded **sequentially with
  `LoadLibraryW` on the init thread**. A mod constructs itself in its `DllMain` (`CompleteModCreation` →
  `Global::CoreMods`), so every mod is complete when `LoadLibraryW` returns, i.e. **before** the game hooks are
  installed. `InitCoreMods` can no longer run while a mod is half-constructed, and the global `Mod::ModRef` is no longer
  written by several mod threads at once.
- Order: discovery unchanged (`mod.ini [Mod] DLLPath`, `<dir>/<dir>.dll`, loose `Content/Mods/*.dll`), then paths are
  `lexically_normal()`ized (backslashes, no `\/`), **sorted case-insensitively by full path**, duplicates removed,
  then BaseMod is moved to the front (same "Moved /BaseMod/BaseMod.dll to front" line). Loading BaseMod first also
  means mods that import `BaseMod.dll` (GameMod is `BASEMOD_API`) resolve it by name from the already loaded module.
- Per mod: `Loading mod <path>` → (mod's own `Mod Created: X`, logger lines) → `Loaded mod <path>`, or
  `Could not load mod <path>: error <code> (<system message>)` with `GetLastError()`.
  Discovered entries that do not exist or are not `.dll` were skipped silently before; now a warning
  `Skipping mod <path>: not an existing .dll file`. After the loop: `Loaded N core mod(s)`.
- Removed a no-op leftover (`if (ModInfoList.size() >= 1) bool empty = …;`) and the unused `<process.h>`.
- Logic-mod registration (`[LogicMod]`) is unchanged and still runs after the DLLs.

## Q8: timing of the pak hooks

Facts:
- `XINPUT1_3.dll` is a **static** import of `Medieval_Dynasty-Win64-Shipping.exe` (pefile; not delay-loaded), so the
  proxy is initialised during process start, before WinMain. The trigger is the first thread created after that.
- The UE log starts with the pak mount (`LogPakFile: Mounting pak file …`) before `Started task graph with … 46 total
  threads` — `FPakPlatformFile` exists and handles lookups from the very beginning of `PreInit`.
- Old log (2026-10-10 smoke test, `Logs/MDML-log.txt`): first MDML line, pak hooks, BaseMod and game hooks are all at
  `02:22:42`, the UE log was opened at `02:22:42`, the first `GameStateHook` at `02:22:46`. Second resolution only.

Reasoning:
- **Before 2.2**, all of `SetupProfile` ran inside MDML's `DllMain`, i.e. while holding the loader lock. Every other
  game thread that started/ended a thread or loaded a DLL in that time (PreInit does both constantly: delay-loaded
  PhysX/Steam/etc., 46 task-graph threads) blocked until `DllMain` returned. The engine was therefore probably
  *paused* during the profile setup. The pak hooks were installed afterwards on the separate `InitHooks` thread,
  which already raced with the game.
- **After 2.2**, the engine is not paused any more: the window from "first thread attach" to "pak hooks live" now
  additionally contains the setup time (`Profile setup took N ms`; in the previous runs the whole setup fit in the
  same second, the PDB lookup is ~0.05 s offline; the **first run** that generates `NoOverwrite.ini` walks all of
  `Content` and can take seconds).
- What can be missed: only files the engine looks up through `FPakPlatformFile` before the hooks are live, i.e.
  early-`PreInit` files (ini configs, plugin descriptors, `AssetRegistry.bin`, shader code libraries, global shaders,
  startup packages / startup movies). Assets loaded for the main menu or a map (blueprints, widgets such as BaseMod's
  `UI_CheatMenu`, meshes, textures) are requested seconds later (`GameStateHook` was 4 s after the hooks) and are not
  affected. Overwrite mods targeting the early files were already racing before 2.2.
- If this turns out to matter, options (not implemented, owner decision): split the setup so the pak-function
  resolution + pak hooks happen first and the rest (NoOverwrite generation, other symbols) afterwards; or generate
  `NoOverwrite.ini` lazily/after the hooks.

What the in-game test must check: the numbers in `Pak overwrites loaded (… ms after process start, … UObjects exist)`.
`0 UObjects` means CoreUObject was not even initialised, so no package can have been loaded yet. A few thousand means
the engine is already loading packages; then only overwrite targets loaded in early `PreInit` are at risk.

## Decisions taken (owner may veto)
1. **Trigger kept**: first `DLL_THREAD_ATTACH` of the proxy (no concrete reason found to change it).
2. **One init thread** in MDML (setup + hooks + mods), no extra thread for `InitHooks`.
3. **Load order**: BaseMod first, then all other mod DLLs alphabetical by full path, case-insensitive; duplicates
   (same normalized path) loaded once. Before, the order was "BaseMod first, rest in directory order", but the
   threads raced so the effective order was random.
4. **Failure reporting**: proxy → `OutputDebugStringW` only (no message box); MDML init failure → Critical log line,
   game continues (no message box, no abort).
5. **Exception guard** around the init thread (see above).
6. **New log lines** (timing, `Loading mod`/`Loaded mod`/`Could not load mod`, `Skipping mod`, `Loaded N core mod(s)`).
   Existing lines were kept verbatim; `Pak overwrites loaded` got a suffix.
7. **`InitCoreMods`' "wasnt setup in time" branch left in place** (file area of the hook bodies, not mine). It is
   unreachable for in-tree mods now (`CompleteModCreation` sets `IsFinishedCreating` before the only `AddToCoreMods`
   call, and loading is synchronous), but `Global::CoreMods.push_back` is public, so a third-party mod could still
   push an unfinished mod. Note: that log call has a comma-operator bug (`Log::Error_UML("…{0}…"), ModName;`), the
   mod name is never formatted. Suggest removing the branch or fixing the message in 3A.
8. `MDML::Start()` → `MDML::Start(HMODULE)` (exported signature change, no external callers).

## Risks
- **Pak-hook timing** (Q8): see above; only early-PreInit file overwrites could be affected.
- **Concurrency with the booting engine**: `SetupProfile` (DbgHelp PDB load with a private session handle, Content
  walk, console allocation) now runs in parallel with the game instead of while the game is blocked on the loader
  lock. DbgHelp is documented as single-threaded; if the engine used DbgHelp at the same moment (stack walk for an
  early ensure/crash) the calls could interleave. Low probability; no engine DbgHelp use expected at startup in
  Shipping.
- **Process exit during init** (first second): the init thread is terminated by `ExitProcess`; if it held the spdlog
  or a CRT lock, `ShutDown`'s logging could block. Same class of risk as the old `InitHooks` thread.
- **Mods' `DllMain` still runs under the loader lock** (mod construction, logger file creation). Unchanged; not in
  scope. A mod whose `DllMain` returns FALSE after `CompleteModCreation` would leave a dangling pointer in
  `Global::CoreMods` (also true before).
- `HookDX` with `DelayGUISpawn=0` and the GUI disabled shows a blocking message box on the init thread; this was on the
  `InitHooks` thread before, and the game hooks are already installed at that point.
