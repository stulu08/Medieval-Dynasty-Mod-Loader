# Wave 2.4: `GameProfile` split into `EngineLayout` / `EngineAddresses` / `LoaderConfig`

Status: done on a worktree branch off `modernize` (2fa4875). Build green. **Awaiting the in-game smoke test.**
Date: 2026-10-10. Plan references: code inventory §7.3 ("What moves where"), §7.5 step 2.4.

## Result in one paragraph

`GameInfo.h` is gone, and with it `class SDK`, `SDK::SelectedGameProfile` and `class GameProfile`. The state it held now
has three owners, each a plain struct with exactly one global instance in namespace `mdml`:
- `mdml::Layout` (`Engine/EngineLayout.h`): engine field offsets.
- `mdml::Addresses` (`Engine/EngineAddresses.h/.cpp`): resolved engine addresses and engine-mode flags.
- `mdml::Config` (`Runtime/LoaderConfig.h/.cpp`): loader paths, switches and the NoOverwrite map.

The UE_LOG logger handle moved next to the macro (`mdml::UnrealLogger` in `Engine/UE4/UE_LOG.h`). The PDB/pattern
symbol resolution moved out of `SetupProfile` into `Engine/EngineAddresses.cpp` as three functions. `SetupProfile`
calls them at exactly the spots where the code used to be, so order and log lines are unchanged. Every call site was a
mechanical rename. No generated SDK file referenced the profile, so none was edited.

## Accessor / export choices

- **One global instance per owner, no accessor functions.** Every call site became `mdml::Addresses.X`,
  `mdml::Layout.X.Y` or `mdml::Config.X`, a one-token change. This is the least churn: about 330 references, 143 of
  them in EngineDefFinder alone. It also keeps hot paths (every offset read in `UObject`/`FProperty` getters) a plain
  memory read. Accessor functions would have changed every expression shape, and in mods every read would become a call
  through the import table.
- **Namespace-scope `extern` variables instead of static class members.** The old `class LOADER_API SDK { static … }`
  existed only to carry the export. Plain `extern MDML_ENGINE_API EngineAddresses Addresses;` does the same, and it
  follows the `mdml::` decision.
- **Exports:**

| Symbol | Macro | Why |
|---|---|---|
| `mdml::Addresses` | `MDML_ENGINE_API` | inline core header code compiled into mods/SDK.lib reads it (`FName::IsUsingNamePool`, `FUObjectArray::IsChunkedArray`, `UClass::CreateDefaultObject`, `FFrame`/`FProperty` `bIsFProperty` checks) |
| `mdml::Layout` | `MDML_ENGINE_API` | not needed by inline code today (all offset reads are in .cpp files), exported so mods/tools (dumps, exporter, DevTools) see the same offsets, as they could before |
| `mdml::UnrealLogger` | `MDML_ENGINE_API` | `UE_LOG` is a macro, expanded in mods (BaseMod `Utils.h`) and SDK.lib |
| `mdml::Config` | `LOADER_API` | BaseMod reads `ImGuiFile` |
| `mdml::LayoutStatus`, `mdml::Resolve*` | not exported | MDML-internal (`SetupProfile`, `UE4::InitSDK`); a mod using them gets a link error |

## SetupProfile split

Moved (commit 2, code and log text unchanged) into `Engine/EngineAddresses.cpp`:
- `Symbols`, now `mdml::Symbols`
- `LogResolved`, `ScanFunction`, `ResolveFunction`, `ResolveGlobal`, all still `static`
- the `#pragma region` blocks, as three functions called from `SetupProfile` at the old spots:

| Function | Was | Called from SetupProfile between |
|---|---|---|
| `ResolveEngineGlobals(GameInfo)` | region "GInfo defs" | `[GameInfo]` flags and "UCore defs" |
| `ResolveEngineFunctions(GameInfo)` | regions "Function defs", "ProcessInternal def", "StaticConstructObject_Internal def" | "UCore defs" and "PakOverwrite" |
| `ResolvePakFunctions(GameInfo)` | the inner part of "PakOverwrite" (only when `bPakOverwrite=1`) | the `bPakOverride` read and `SymbolResolver::Shutdown()` |

What stays in `SetupProfile` (MDML.cpp):
- the ini reading: paths, log dir, console, loggers, GUI/DX11, profile path, NoOverwrite generation/parse, `[Overwrites]`, `[GameInfo]` flags
- the "UCore defs" (layout from ini)
- `SymbolResolver::Init/Shutdown`

Moving the ini reading into `Runtime/LoaderConfig.cpp` (and NoOverwrite into `Mods/OverwriteMods.cpp`) is the 3A Runtime
split in the plan. I did not do it here, because it means restructuring `SetupProfile` around `Log::Init` and the
console setup. That is not mechanical.

`StringToDWord` stays defined in `MDML.cpp`. `EngineAddresses.cpp` forward-declares it, the same style `MDML.cpp`
already used. `MDML.cpp` no longer needs `Utilities/Pattern.h`, so that include was dropped.
`EngineAddresses.cpp` includes `Pattern.h`, `SymbolResolver.h`, `Logger.h` and `INI.h`. The Engine layer now
depends on the Platform-level utilities, which is the allowed direction in §7.1.

Init-thread order (2.2) is untouched. `InitThread` → `SetupProfile` → `HooksManager::SetupHooks`, and inside
`SetupProfile` the same statements run in the same order.

## Decisions taken (owner may veto)

- **D1 – Names.**
  - Types: `mdml::EngineLayout` (was `Offsets`), `mdml::EngineLayoutStatus`, `mdml::EngineAddresses`, `mdml::LoaderConfig`.
  - Instances: `mdml::Layout`, `mdml::LayoutStatus`, `mdml::Addresses`, `mdml::Config`, `mdml::UnrealLogger`.
  - These are not `UE4::`, because they are MDML's description of the engine, not mirror types.
  - Field names were kept verbatim, typos included (`IsUsingDeferedSpawn`, `bPakOverride` for the ini key `bPakOverwrite`), to keep the diff a pure rename. Fixing them belongs to the typo pass (§7.4).
- **D2 – Hook targets in `EngineAddresses`.** `GameStateInit`, `BeginPlay`, `Tick`, `ProcessInternals` and the two pak functions are only used by the loader (HooksManager, `CreateMod`). They are still resolved engine addresses, from the same resolver, so they stay together. The header groups them under "Hook targets". The alternative is to move them to a loader-side struct in 3A.
- **D3 – UE logger handle next to `UE_LOG.h`, not in `LoaderConfig`.** `UE_LOG.h` is an engine-core header. Making it include `Runtime/LoaderConfig.h` would make the Engine layer depend on Runtime, which is upward. So it is `mdml::UnrealLogger` in `UE_LOG.h` (exported, defined in `EngineInit.cpp`). `UE_LOG.h` now includes `Core.h` itself, for `Ref`/`MDML_ENGINE_API`; it already depended on `Core.h`'s `LogLevel`. `MDML::UnrealEngineLoggerInstance` (the `Logger` wrapper that owns it) is unchanged.
- **D4 – `LayoutStatus` separate and not exported.** The "missing" flags are bookkeeping for the runtime scan. They disappear with PDB constants (3D), so they are not part of `EngineLayout`. That keeps `EngineLayout` a pure offset struct, ready for 3D. They were exported before, as part of the profile, but nothing outside MDML uses them.
- **D5 – Engine-mode flags in `EngineAddresses`** (per the task), not in `EngineLayout`. Several of them (`UsesFNamePool`, `IsUsingFChunkedFixedUObjectArray`, `bIsFProperty`) are really layout choices. If 3D drops the UML paths (Q3), most of these flags go away anyway.
- **D6 – `Layout` definitions in `EngineInit.cpp`.** No `EngineLayout.cpp`, see "Files".
- **D7 – Two dead fields removed** (`IsGInfoPatterns`, `IsFunctionPatterns`). Never read or written. The `Dumper` output text `IsGInfoPatterns=0` is an ini key it writes, unaffected.
- **D8 – No forwarding `GameInfo.h`.** Removing it did not cascade: no generated file, ExampleMod or proxy included it.
- **D9 – SetupProfile only partly split** (symbol resolution out, ini reading in). See above; the rest is 3A.

## Behaviour changes

None intended. Things that are technically different:
- **Exported symbol names changed.** The old `?SelectedGameProfile@SDK@@2VGameProfile@@A` is gone. The new data exports are `mdml::Addresses`, `mdml::Layout`, `mdml::Config` and `mdml::UnrealLogger`. Old mod DLLs that imported `SelectedGameProfile` will fail to load against the new MDML.dll. Deploy all DLLs together, as already required since 2.3.
- **Static-init order:** the five instances live in three translation units instead of one. Nothing reads them during static initialization; the first reader is the init thread.
- The `Symbols` namespace is now `mdml::Symbols`, file-local in use.

## In-game smoke test (owner)

Deploy the whole `bin/Release-windows-x86_64` output together: `MDML.dll`, `xinput1_3.dll`, `Config/` and `Mods/*`.

1. Start the game and reach the main menu. Compare `Logs/MDML-log.txt` with the previous run. These must be identical except timestamps:
   - the resolve lines `GName: 0x… (pdb, rva …)`, `GObject`, `GWorld`, `GameStateInit`, `BeginPlay`, `Tick`, `StaticLoadObject`, `StaticFindObject`, `SpawnActorFTrans`, `CallFunctionByNameWithArguments`, `ProcessEvent`, `CreateDefaultObject`, `GetDisplayNameTextByIndex`, `ProcessInternals`, `StaticConstructObject_Internal`, and the pak functions if `bPakOverwrite=1`. Same order, same rvas.
   - `Setup Config/…profile`, `Pak overwrites loaded`, `Loaded N core mod(s)`, `Loader setup finished`
   - then `All Engine Classes Found` and `Engine Classes Loaded`
2. `Logs/UE_LOG-log.txt` is still created. It is written only when the core hits a `UE_LOG` path, so it may stay empty.
3. Press F1: the UI opens, and its window layout is restored from `Config/WindowConfig.ini` (`mdml::Config.ImGuiFile`). In BaseMod, use the feature that lists the `Config` folder (it reads `ImGuiFile`'s parent folder).
4. BaseMod object browser: list classes, actors and packages. This exercises offsets and `bIsFProperty` in a mod through the imported `mdml::Addresses`.
5. Load a save. If a logic mod is installed, it spawns (`BeginPlayOverwrite`, `ProcessInternals` hook, `StaticConstructObject_Internal`). TimeWeatherChanger reads and writes time/weather.
6. If overwrite mods are enabled: the links are created (`Created N … links`), and loose game files listed in `NoOverwrite.ini` still load from the game, not from a mod.
7. Optional: the loader's "Engine info dump" (`Dump/EngineInfo.txt`) shows the same values as before.
8. Quit; check that the shutdown is clean.
