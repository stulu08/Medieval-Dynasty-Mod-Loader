# Wave 2.3: hand-written engine core moved into MDML.dll and exported

Status: done on a worktree branch off `modernize` (f9acdc2). Build green. **Awaiting the in-game smoke test.**
Date: 2026-10-10. Plan references: `docs/MODERNIZATION_PLAN.md` (decision "Core location"), code inventory §7.5 step 2.3.

## Result in one paragraph

The hand-written UE core now lives in `ModLoader/src/Engine/` and is compiled into `MDML.dll`. Its classes and static
data are exported with a new macro, `MDML_ENGINE_API`. There is exactly one `UObject::GObjects`, one `FName::GNames`
and one `UWorld::GWorld` in the process. Every mod and every `SDK.lib` object imports them from `MDML.dll`. `SDK.lib` now
holds only generated code, the two aggregators and the hybrids. `MDML.dll` no longer links `SDK.lib`, so the SDK ⇄ MDML
link cycle is gone, and with it the 7× LNK4286 warnings. Mods no longer call `UE4::InitSDK()`. MDML initializes the
engine once, at the same point as before.

## Export macro: `MDML_ENGINE_API`

Defined in `ModLoader/src/Core.h` as `#define MDML_ENGINE_API LOADER_API`. It uses the same import/export switch
(`UNREALENGINEMODLOADER_EXPORTS`).

Why a separate name instead of reusing `LOADER_API`:
- Engine exports stay greppable and are clearly separated from the loader/mod API.
- The plan (code inventory §7.2) already uses this name.
- If the owner ever wants the core in its own DLL (inventory §8 Q1 alternative), only this one line changes.

It behaves exactly like `LOADER_API` today.

What is exported:
- Classes:
  - `UObject`, `UPackage`
  - `UField`, `UEnum`, `UStruct`, `UScriptStruct`, `UClass`, `UFunction`, `UDynamicClass`
  - `FName` (holds `GNames`)
  - `FFieldClass`, `FField`, `FProperty` and **all** 29 `F*Property` subclasses
  - `UWorld` (holds `GWorld`)
  - `UUserDefinedEnum`
- Free functions: `UE4::StringifyFlags` (3 overloads) and `NameValidator::*` (4 functions).
- In total, MDML.dll now has 347 engine exports, including `?GObjects@UObject@UE4@@…`, `?GNames@FName@UE4@@…` and `?GWorld@UWorld@UE4@@…`.

Not exported, because they are header-only or plain data:
- `Containers/*`, `Math/*`, `FNamePool*` and `FUObjectArray`/`ObjectsArray`
- `FKey`, `FFrame`
- Templates: `TSubclassOf`, `TScriptInterface`, `GetVariable`/`SetVariable`, `FindObject<T>`, …
- The trivial Engine stubs (`ULevel`, `UGameInstance`, `AGameState`, `UUserDefinedStruct`, `UBlueprintGeneratedClass`, `UBlueprintFunctionLibrary`, `ACustomClass`)
- The generated CoreUObject structs in `CoreTypes.h`

`ACustomClass` is deliberately **not** exported. Its `StaticClass(std::string)` caches the *first* class it is ever
asked for in a function-local static (an existing bug). If it were exported, that cache would become shared across DLLs.

## How the cycle was resolved

Before this change:
- MDML.dll linked SDK.lib.
- SDK.lib's core objects were dllimport-compiled against MDML.dll. That caused the LNK4286 warnings.

Plan: the core moves into MDML, and SDK.lib imports from MDML. The only remaining problem was that MDML itself calls 7 **generated**
functions. The linker listed exactly these when SDK.lib was dropped:

| Symbol | Used in | Generated file |
|---|---|---|
| `UGameplayStatics::GetGameInstance(UObject*)` | `MDML.cpp` (logic-mod persistent object) | `GamePlayStatics.cpp` |
| `UGameplayStatics::BeginDeferredActorSpawnFromClass(…)` | `MDML.cpp` (`SpawnActor`, deferred path) | `GamePlayStatics.cpp` |
| `UGameplayStatics::GetCurrentLevelName(UObject*, bool)` | `Dumper.cpp` | `GamePlayStatics.cpp` |
| `UGameplayStatics::ExecuteConsoleCommand` (hand-written part of the hybrid) → `UKismetSystemLibrary::ExecuteConsoleCommand` | `LoaderUI.cpp` (console box) | `GamePlayStatics.cpp`, `KismetSystemLibrary.cpp` |
| `AActor::K2_GetActorLocation/K2_GetActorRotation/GetActorScale3D` | `Dumper.cpp` (world actor dump) | `Actor.cpp` |

**Choice: compile those three generated `.cpp` files into MDML.dll as well, straight from `SDK/src/UE4/Engine/`.**
This is a premake `files` entry in `ModLoader/premake5.lua`, built without PCH. They are not exported. SDK.lib keeps
its own copy for the mods, so each DLL has its own copy of these wrappers. That is exactly how it was before: MDML pulled
the same objects out of SDK.lib. There is no source edit, no generated file is moved into the hand-written core, and the
call sites in `MDML.cpp`, `LoaderUI.cpp` and `Dumper.cpp` stay untouched. Agents A and D are editing those files in parallel.

Alternatives I rejected:
- **Hand-written by-name replacements at the call sites.** These are cleaner long-term, but they mean edits in A's and D's files during parallel work.
- **Hand-written definitions of those 7 symbols.** That duplicates generated code by hand.
- **Moving the three generated files into the core.** That would make generated code look hand-written.

All three can be revisited when the 2.4 generator replaces the old SDK. At that point, MDML needs its own way to call
these 4 engine functions anyway (see open question Q2).

Link graph now:
- `MDML.dll` links only MinHook.
- `SDK.lib` is a static lib with no links. Every object in it references `__imp_…` engine symbols, so **anyone who links SDK.lib must also link MDML.lib**. A comment in `SDK/premake5.lua` says so.
- BaseMod links `MedievalDynastyModLoader`, `SDK` and `MinHook`.
- The examples link `BaseMod`, `SDK`, `MedievalDynastyModLoader` and `MinHook`. These link lists did not change.
- MDML and SDK no longer depend on each other, so they now build in parallel.

## Engine initialization

- `UE4::InitSDK()` used to be a `static` function in `MDML.h`, so every DLL had a copy.
  - Inside MDML it bound the globals and ran `EngineDefFinder`.
  - Inside each mod, called from the `GameMod` constructor, it only bound that mod's own copies of the globals.
- Now `MDML.h` only declares two functions. They are MDML-internal and not exported, so a mod that still calls `InitSDK` gets a link error instead of silently doing something:
  - `UE4::InitEngineGlobals()` binds `GObjects`, `GNames` and `GWorld` from `SDK::SelectedGameProfile`. It is idempotent.
  - `UE4::InitSDK()` calls `InitEngineGlobals()` and then runs the unchanged `EngineDefFinder` block.
- Both are defined in `Engine/EngineInit.cpp`. The bodies are moved verbatim. The old `#ifdef UNREALENGINEMODLOADER_EXPORTS` guard went away because the code now only exists in MDML.
- The call site is unchanged: `MDML::InitCoreMods()` (first `InitGameState`).
- `GameMod`'s constructor no longer calls anything.

**Why this keeps behaviour.** Mods register their events (Tick, DrawImGui, BeginPlay, …) in `InitializeMod()` →
`SetupHooks()`. `InitCoreMods()` calls that only **after** `InitSDK()`. So before this change, no mod event could run
earlier than the moment MDML now binds the globals. I checked the code paths that run earlier:
- The mod constructors in BaseMod, PresetMod and TimeWeatherChanger.
- `OnModMenuButtonPressed`, called directly from LoaderUI.

None of them touches the engine. Even where one did, it was effectively broken before: `defs` offsets are only scanned
in `InitSDK`, so early engine calls in mods would have read with zero offsets.

I first tried binding the globals in `Mod::CompleteModCreation()`. I reverted it: that would have changed MDML's own
early window. For example, the F1 "dump objects" tool checks `GObjects != nullptr` and would have started running before
the offsets are scanned.

## Include cleanup

- `UE4.h` no longer includes `Utilities/Pattern.h` or `GameInfo.h`. `NamePool.h` no longer includes `Pattern.h`.
- `Pattern.h` is now included explicitly where it is used:
  - `Engine/UE4/Engine/UserDefinedEnum.cpp`
  - `ModLoader/src/MDML.cpp`: a one-line include, outside my area. See "Files touched outside my area".
- `GameInfo.h` is still reached transitively, because the core headers read `SDK::SelectedGameProfile` (`NamePool.h`, `ObjectsArray.h`, `UE_LOG.h`, …). It goes away with the `GameProfile` split (inventory §7.5 2.4).
- Former siblings now use `"Engine/…"` paths:
  - `World.h`: `"Engine/Structs.h"`
  - `GameState.h`: `"Engine/GameStateBase.h"`
  - the hybrid `SDK/src/UE4/Engine/GamePlayStatics.h`: `"Engine/World.h"` and `"Engine/BlueprintFunctionLibrary.h"`. This is an include-path-level fix in a generated/hybrid file. Declarations are unchanged.

Still true, and out of scope here: the core is **header-coupled** to the generated SDK.
- `World.h` includes the generated `Engine/Actor.h` and `Engine/Structs.h`.
- `GameState.h` derives from the generated `AGameStateBase`.
- `Object.cpp`, `Class.cpp`, `UserDefinedEnum.cpp` and `NameValidator.cpp` include the whole SDK through `SDK.h`/`UE4.h`.

So MDML still needs the `SDK/src*` include dirs, for headers only. Cutting this is part of 3D / 2.4.

## Decisions taken (owner may veto)

- **D1 – Macro.** I added `MDML_ENGINE_API` as an alias of `LOADER_API`, instead of reusing `LOADER_API` directly. Reasons are above.
- **D2 – Cycle.** MDML compiles `Actor.cpp`, `GamePlayStatics.cpp` and `KismetSystemLibrary.cpp` from `SDK/src` a second time, not exported. The alternative is by-name or hand-written calls in MDML.
- **D3 – NameValidator moved into the core.** It was not on the move list; the plan sends it to DevTools later. But the exported `FProperty` subclasses' inline `GetCppType()` call `NameValidator::*`. If it stayed in SDK.lib, MDML would need SDK.lib again, which brings back the cycle. It is exported. BaseMod's exporter uses it through the import.
- **D4 – Hybrids.**
  - `CoreTypes.h/.cpp` moved **whole**. The generated region consists of data-only CoreUObject struct declarations with no functions. It is unchanged, just in a new folder, and splitting it would not have bought anything yet.
  - `GamePlayStatics.*`, `DataTable.*` and `StringTable.*` **stay in SDK unsplit**. Their generated part dominates. MDML uses `GamePlayStatics` only through D2. `DataTable` and `StringTable` are used only by mods, through SDK.lib.
  - Splitting off the hand parts would need new files plus generated-file edits. Better done when 2.4 replaces them. The hand parts are listed in code inventory §1.2.
- **D5 – `UE4/SDK.h` stays in SDK**, because of the 346 relative `"../SDK.h"` includes in generated files. `UE4.h` did move: it is a hand-written umbrella that must survive the SDK regeneration.
- **D6 – Whole reflection hierarchy exported**, including the header-only property classes. This avoids C4275 (an exported class with a non-exported base) and is easy to explain. The cost is a few hundred extra exports.
- **D7 – No `dependson` from SDK to MDML.** SDK.lib does not need MDML.lib to build, and this lets them build in parallel. The mod projects link both, as before.
- **D8 – Engine init timing unchanged.** The init runs at `InitCoreMods`, not at mod creation (see "Engine initialization"). `InitEngineGlobals()` is split out so that startup (agent A) can call it right after the addresses are resolved, if wanted.

## Behaviour changes to be aware of

- **Function-local static caches in exported inline functions are now shared across DLLs.** MSVC imports inline member functions that contain a static local from the DLL instead of inlining them. pefile shows mods importing `UClass::StaticClass`, `UEnum::StaticClass`, `FStructProperty::StaticClass` and others from MDML.dll. The cached values (`FindClass("Class CoreUObject.X")`) are identical in every DLL, so this is harmless. It does mean that whoever calls first fills the cache for everyone. If something ever calls one of these before the offsets are scanned and caches `nullptr`, every DLL sees `nullptr` from then on. Today nothing calls them that early (see "Engine initialization").
- Per-DLL caches remain in:
  - generated wrappers (`static auto fn = FindObject<UFunction>(…)`)
  - `FNamePool::GetNext`
  - `ACustomClass`
  - template instantiations
- **Deploy all DLLs together.** Old mod DLLs carry their own core copy and an inline `InitSDK`. They do not import the new engine symbols, but they would still work in isolation. Mixing old and new builds is untested; don't do it.

## In-game smoke test (owner)

Deploy the whole `bin/Release-windows-x86_64` output: `MDML.dll`, `xinput1_3.dll`, `Config/` and `Mods/*` together.

1. Start the game and reach the main menu. Check `Logs/MDML-log.txt`:
   - the symbols resolve as before
   - `UObject Not Defined. Scanning for def.` (etc.) appears, followed by **`All Engine Classes Found`** and `Engine Classes Loaded`
   - BaseMod is created and initialized
   - there are no new errors
2. Press F1: the UI opens. In BaseMod's **object browser**, list classes, actors and packages. This uses the shared `GObjects` and `FName` from MDML in a mod.
3. Load a save, then use the F1 **console command** box with a harmless command (e.g. `stat fps`). This uses `ExecuteConsoleCommand`, which is now compiled into MDML.
4. In the loader's tools, run the **world-actor dump**. This uses `GetCurrentLevelName` and `AActor::K2_GetActor*`, now compiled into MDML.
5. If installed: in TimeWeatherChanger, read and change the time or weather. That is reflection by name in a mod.
6. Optional, if a logic mod is available: spawning it exercises `SpawnActor`, `GetGameInstance` and `StaticConstructObject`.
7. Quit and check for a clean shutdown.

## Risks / open questions

- **Q1 (agent A coordination):** `MDML.cpp` now includes `Utilities/Pattern.h` explicitly, because `UE4.h` no longer pulls it in. If A moves `SetupProfile`/pattern code to a new file, that file needs the include too. Otherwise the merge build fails with an obvious "`Pattern` is not a namespace" error. A may also call `UE4::InitEngineGlobals()` right after the GName/GObject/GWorld addresses are resolved. That is optional; nothing needs it today.
- **Q2 (2.4):** once the old generated SDK is replaced, MDML still needs `GetGameInstance`, `BeginDeferredActorSpawnFromClass`, `ExecuteConsoleCommand` and the actor transform getters. They should become hand-written by-name calls in the core, which removes D2.
- **Q3:** should the hybrids' hand parts be split now? I did not split them; see D4.
- **ABI** (code inventory §7.6): mods now depend on MDML.dll's C++ class exports. Same MSVC toolset and `/MD` are required. That was already true for `Mod` and `Global`.
- **Stale doc paths.** I did not edit these, per instructions or because they are historical:
  - `docs/REVERSE_ENGINEERING.md:70` mentions `SDK/src/UE4/CoreUObject/Class.h:94`. The file is now `ModLoader/src/Engine/UE4/CoreUObject/Class.h`.
  - The code inventory and the plan's "Hand-written SDK core" section still show the old `SDK/src` paths.
- The `CLAUDE.md` "Layout" rows need updating. A proposal follows.
